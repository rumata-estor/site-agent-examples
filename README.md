# Site Agent Runtime — примеры инженерных решений

Три компонента закрытого проекта Site Agent Runtime: исходный код, тесты и интерактивные проверки. Это **не полный Runtime** и не готовый продукт.

| Компонент | Исходный код | Состояние публичной версии |
| --- | --- | --- |
| Task Manager | [`siteagent/tasks.py`](siteagent/tasks.py) | Исправлена согласованность указателя активной задачи; добавлены тесты. |
| ChangeSet | [`siteagent/changesets.py`](siteagent/changesets.py) | Защита от гонок и подмены черновика; недоверенные подтверждения запрещены. Добавлены тесты и демонстрация. |
| State Guard | [`siteagent/state_guard.py`](siteagent/state_guard.py) | Исправлена конкурентная запись маркеров и проверка целостности; добавлены тесты и демонстрация. |

ChangeSet получает состояние задачи от Task Manager, данные решений — через DecisionStore, а разрешённые объекты и операции — от Resolver. State Guard хранит маркеры устаревшего состояния, которые ChangeSet учитывает перед фиксацией. Полных реализаций TaskSpec, DecisionSet и Resolver здесь нет: в проверках используются синтетические зависимости.

## Task Manager: инженерное решение

Task Manager хранит состояние задачи отдельно от переписки: жизненный цикл, разрешённые переходы, контрольные точки и журнал результатов. Записи сохраняются в JSON с атомарной заменой файлов; операции сериализуются через `fcntl.flock`.

Файл задачи и `active.json` нельзя обновить одной атомарной операцией. После сбоя между записями указатель на активную задачу может оказаться устаревшим. Поэтому он восстанавливается по записям задач под блокировкой:

- Ровно одна задача в `running` или `verifying` становится активной.
- Две занятые задачи или повреждённая запись — ошибка с диагностикой, без автоматического выбора.
- Если занятых задач нет, текущей может оставаться `paused` или `blocked`; ссылки на завершённые или удалённые задачи очищаются.
- Вторую занятую задачу нельзя создать, пока существует первая.

Цена восстановления — обход сохранённых задач. Решение рассчитано на небольшой каталог с приоритетом корректности.

## ChangeSet: инженерное решение

ChangeSet описывает объекты изменений, ожидаемые результаты, проверки, резервирование и откат. План валидируется и привязывается к разрешённым объектам и операциям, переданным Resolver в рамках TaskSpec; затем вычисляется канонический SHA-256 отпечаток. Зафиксированный план нельзя перезаписать через `set()`: поправки оформляются через `amend()`, который возвращает план в черновик.

В исходной реализации были гонки между подготовкой, изменением и фиксацией плана. В публичной версии перед записью черновика **под файловой блокировкой** проверяется, не изменился ли ранее прочитанный документ. Перед `seal()` под той же блокировкой проверяются актуальность исходных данных, соответствие содержимого черновика сохранённому SHA-256 отпечатку и отсутствие требования подтверждения. Подмена уже зафиксированного плана обнаруживается при проверке его состояния.

Доверенного механизма подтверждения полномочий в репозитории нет: `approve()` всегда отказывает, даже при `source="user"`. Фиксировать можно только планы, не требующие подтверждения. При `amend` прежнее утверждение не наследуется. **Планы здесь не исполняются.**

## State Guard: инженерное решение

`canonical_hash` рассчитывает SHA-256 канонической JSON-структуры. `StaleStateStore` хранит маркер `STALE_STATE` с ревизией и диагностикой, позволяющий определить, что данные были признаны устаревшими после чтения. Маркер создаётся по вызову другого компонента: State Guard не наблюдает за изменениями сайта самостоятельно.

State Guard **не выполняет compare-and-swap в CMS**. Отклонить запись с устаревшей версией должен исполняющий адаптер; в браузерном примере он синтетический.

В исходной реализации два параллельных вызова могли записать одинаковую ревизию. В публичной версии чтение и увеличение ревизии защищены `fcntl.flock`. Повреждённые маркеры и маркеры с неверной идентичностью не перезаписываются молча. Временные метки сравниваются с учётом часового пояса; некорректные метки отклоняются.

## Интерактивная демонстрация в браузере

**[▶ Открыть интерактивные проверки на GitHub Pages](https://rumata-estor.github.io/site-agent-examples/)**

Три вкладки, по три последовательных действия в каждой:

- **Task Manager:** запустить задачу → попытаться запустить вторую (отказ) → завершить первую.
- **ChangeSet:** подготовить обычный план → проверить план высокого риска → попытаться подтвердить его без доверенного разрешения (отказ).
- **State Guard:** два агента читают один текст → агент А изменяет его → агент Б пытается записать устаревшую версию (отказ и `STALE_STATE`).

После каждого действия показаны состояние, результат и причина отказа. Сценарии запускаются повторно кнопкой «Начать сначала». Исходники и результаты тестов доступны по ссылкам в интерфейсе.

Браузер исполняет опубликованные Python-модули через Pyodide с синтетическими зависимостями, без подключения к сайтам. Проверка версии в State Guard выполняется тестовым адаптером, а не реальной CMS. Межпроцессные `fcntl.flock` проверяются в Linux / GitHub Actions, не в Pyodide.

## Проверки на GitHub

[**Результаты автоматических тестов в GitHub Actions**](../../actions/workflows/task-manager-tests.yml)

Проверяются:

- **Task Manager:** переходы состояний, checkpoints, запрет второй активной задачи, восстановление после сбоя, повреждённые записи и конкурентное создание в потоках и процессах.
- **ChangeSet:** границы TaskSpec, секретные поля, высокий риск, запрет поддельного подтверждения, устаревшие планы, запрет фиксации изменённого черновика, обнаружение подмены зафиксированного плана, `amend` и конкурентные записи.
- **State Guard:** канонические отпечатки, устаревшее состояние, временные метки с разными UTC-смещениями, ревизии, конкурентные записи в потоках и процессах, повреждённые маркеры.

Локальный запуск на Linux с Python 3.10–3.13 без сторонних библиотек:

```bash
git clone https://github.com/rumata-estor/site-agent-examples.git
cd site-agent-examples
python3 -m unittest discover -s tests -v
```

Тесты выполняют реальную логику `TaskStore`, `ChangeSetStore` и `StaleStateStore` с файловыми операциями. Отсутствующие интеграции заменены синтетическими `DecisionStore`, `Resolver` и функциями окружения; для воспроизведения отдельных гонок инструментируется чтение документов. GitHub Actions проверяет Python-компоненты на Linux с Python 3.10–3.13, включая отдельный запуск каждого тестового модуля, но не браузерный интерфейс.

## Границы безопасности

Опубликованные компоненты не управляют работающими сайтами: здесь нет полного Executor и независимого контроллера подтверждения полномочий. ChangeSet не принимает подтверждение человека без доверенного механизма. SHA-256 отпечатки не заменяют защиту файлового хранилища от прямого изменения данных. **Этот код нельзя использовать как готовую систему безопасного исполнения изменений.**

Независимого аудита безопасности не проводилось.

Исходный код опубликован исключительно для изучения архитектуры, демонстрации инженерных решений и некоммерческого тестирования. Проект **не является Open Source** или готовым программным продуктом.
